# What's My Name: A Name Constraints Test Suite

X.509 certification validation is hazardous enough. Name constraints are nightmare mode.
They are incompletely specified. In several cases later RFCs modify or even completely
reverse the rules that were laid down in earlier RFCs. In at least one case, the RFC
required validation step is completely insecure. (Happily, nobody has read that RFC.)

This is a set of test cases derived from the requirements of RFC 5280 and successor RFCs,
as well as test cases that specifically poke at every known security vulnerability which
affected name constraint processing in Botan, GnuTLS, Go, and OpenSSL.

## How to use

`generate_nc_chains.py` parses the testcase DSL and generates the chains.

```sh
./generate_nc_chains.py testcases --out chains
```

By default ECDSA is used and everything is deterministic (keys and serial numbers are generated by
hashing). If you need RSA use ``--key-type rsa`` however then the output of each run will be
randomized.

## How to check

`test_nc_chains.py` verifies the chains using several validators (Botan, OpenSSL, and GnuTLS using
their respective command line tools, and Go and rustls-webpki via the command line tools in
`go-verify` and `rust-verify`). You can also exclude validators using `--no-openssl`, `--no-gnutls`,
etc. If all validators agree then nothing is printed for that test (unless you used `--verbose`), so
the default output is exactly the cases where there is divergence between implementations.

## Fun Facts We Learned

### OpenSSL

* An intermediate with a name constraint excluding issuance for DNS `foo.example.com` can sign a
  leaf with a SAN of `*.example.com`, which OpenSSL will then accept as a valid certificate for
  `foo.example.com`. [Reported; OpenSSL says this seems fine.]

### AWS-LC

* Email name constraint parsing was fooled by quotes; a name constrained CA excluded from issuing
  names for `example.com` could issue an email adddress `"a@b"@example.com`. [Reported; known issue]

### Python-cryptography

* An intermediate with a name constraint allowing it to issue only for the DNS name `foo.example.com` could
  issue a certificate with a wildcard DNS SAN of `*.example.com`, allowing it to escape the permitted
  subtrees. [Reported, fixed in version 49; https://github.com/pyca/cryptography/security/advisories/GHSA-m2h6-j472-rp4c]

* Python-cryptography accepted certificates with contain critical name constraints on the DN, then
  completely ignored them, accepting leafs with violating DNs. [Reported, fixed in version 49]

### GnuTLS

* GnuTLS's URI permittedTree checking accepts certificates with any names, as long as *one* of the
  names is inside the permittedTree. [Reported May 20]

* GnuTLS accepts, but does not enforce, permittedName constraints for directoryNames.
  [Reported May 20]

### Go

* An email name constraint of `example.com` allows a SAN like `user@example.com` but does not
  authorize subdomains (`user@corp.example.com`). Golang accepts this deviation.
  [CVE-2026-78664 https://github.com/golang/go/issues/81280]

### LibreSSL

* URI parser is vulnerable to userinfo smuggling; an intermediate with a permitted URI tree of
  `example.net` can issue a leaf with a SAN of `https://example.net:443@attacker.com/path` -
  the `example.net:443` is the URI userinfo string, `attacker.com/path` is the address.
  [Fixed in https://github.com/libressl/openbsd/commit/d9a371b178de7043470c89bef81aa96da20dc855]

### wolfSSL

* wolfSSL applies name constraints, but only to the next certificate in the chain. A certificate with
  name constraints applied to it can simply issue another intermediate certificate with no names and
  no new name constraints. That intermediate in turn can mint certificates with any name.
  [Reported, fixed]

* wolfSSL's path validator API (CertManager) has no way of expressing an untrusted intermediate, and
  if an intermediate is added through the trusted certificate flow, name constraint checking is
  completely skipped. [Clearly intentional behavior but ... ???]
